# 监测方法与技术实现

本文定义项目对“延迟、丢包、可达性”的准确含义，也是实现、历史存储和面板必须共同遵守的技术契约。

## 1. 设计目标

- 一个 Agent 二进制和一种配置结构适用于任意 Linux VPS。
- 基础主机监控始终存在；服务检查和通信探针按配置叠加。
- Agent 只发起出站连接，不监听端口、不执行远程命令、不修改业务服务。
- 通信探针只实现明确启用的 ICMP Echo 或 TCP Connect；不携带 TLS、HTTP、登录或任意命令能力。
- **只采集、上报和保存页面或 Telegram 会展示的数据**；没有展示的指标不采集、不计算，也不存储。
- 使用当前数据库结构与上报格式；Worker 上线后逐台更新 Agent，并确认配置与新上报。

## 2. 通信探针语义

| 类型 | 实际操作 | 延迟含义 | 失败的表现 | 适用场景 |
| --- | --- | --- | --- | --- |
| `icmp` | ICMP Echo 请求/响应 | 网络层 RTT | **丢包率** | 节点间基础链路质量、目标允许 ICMP 时 |
| `tcp` | TCP 三次握手后立即关闭 | 建立 TCP 连接的耗时 | 本轮**连接失败** | ICMP 被过滤、需要观察指定端口能否连上时 |

ICMP 丢包只能说明 Echo 报文未返回；它可能来自真实链路丢包，也可能来自目标或中间设备的 ICMP 限速或过滤，不能单独证明某个应用服务不可用。

TCP 探针只报告延迟和本轮是否连上，不计算失败比例。连接失败可能来自链路、ACL、防火墙、监听服务或连接队列，不能单独定位根因。TCP 探针不发送 TLS ClientHello、HTTP 请求或应用数据，因此也不证明上层协议可用。

## 3. 单轮采样

每个探针按以下顺序运行：

1. 校验配置中的探针类型和目标格式；不接受命令行片段或任意 shell 输入。
2. 目标必须是单独的主机名或 IP；ICMP 不接受端口，TCP 另用受限整数 `port` 字段，任何类型都不接受 URL 或 shell 片段。
3. 按 `samples` 发起 1–10 次测量，相邻启动时间由 `sample_interval_ms` 控制。
4. `timeout_seconds` 是整轮上限。若时间耗尽，未启动的样本不会伪装成失败样本，该轮记为未完成。
5. Agent 上报请求数、实际尝试数、成功数和代表延迟。

ICMP 默认 5 个样本，TCP 默认 3 个样本，间隔均为 250 ms。ICMP 配置必须满足：

```text
(samples - 1) × sample_interval_ms < timeout_seconds × 1000
```

TCP 还必须将单次 `connect_timeout_ms` 纳入整轮上限：

```text
(samples - 1) × sample_interval_ms + connect_timeout_ms
≤ timeout_seconds × 1000
```

不同目标的探针最多并行运行两项；同一探针的一轮样本按配置间隔启动。

## 4. 指标定义

设请求样本数为 `N`，实际尝试数为 `A`，成功数为 `S`，成功 RTT 集合为 `R`：

```text
ICMP 丢包率 = (A - S) / A × 100%       （A > 0；A = 0 记为 100%）
```

- `duration_ms`：`R` 的中位数，作为一轮的代表延迟；
- 一轮只有在 `A = N` 且 `S > N/2` 时才标记为成功；`complete=false` 表示采样未完成，不能与目标丢包混为一谈；
- TCP 一轮失败（连不上）时，首页延迟值显示为红色“— ms”，对应的延迟格变红，节点状态按探针级别变为“异常”或“需关注”。

丢包率由 Worker 根据 `A` 与 `S` 计算，Agent 不再单独上报百分比。

## 5. 权限模型

Agent 直接使用 [`prometheus-community/pro-bing`](https://github.com/prometheus-community/pro-bing)，并固定为非特权模式 `SetPrivileged(false)`。Linux 上它使用 datagram ping socket，因此 systemd unit 继续保持：

- `User=vpsmon`；
- `NoNewPrivileges=true`；
- 空的 `CapabilityBoundingSet` 和 `AmbientCapabilities`；
- 不授予 `CAP_NET_RAW`，不以 root 运行。

主机内核的 `net.ipv4.ping_group_range` 必须允许 `vpsmon` 用户组使用非特权 ping socket。若发行版禁用了它，ICMP 探针会一直失败；项目不会静默切换到特权 raw socket。

TCP 使用 Go `net.Dialer` 发起普通出站连接，不需要额外 capability，也不监听入站端口。


## 6. 历史存储与状态分级

D1 只保存页面会读取的历史：

| 数据 | 保留 | 用途 |
| --- | ---: | --- |
| 每分钟上传／下载速率、每轮探针结果 | 30 天 | 首页格栅、6 小时到 30 天的详情图 |
| 每日平均速率、每日探针汇总 | 90 天 | 90 天详情图 |
| 节点事件 | 90 天 | 详情页事件列表 |

每轮探针结果只保存名称、时间、是否成功、代表延迟、尝试数和成功数；每日汇总保存轮次、成功轮次、平均延迟和成功样本率。

页面按下表读取：

| 页面视图 | 时间范围 | 输出时间桶 |
| --- | ---: | ---: |
| 首页全节点能量格 | 24 小时 | 5 分钟 |
| 单节点详情 | 6 小时、24 小时 | 1 分钟 |
| 单节点详情 | 7 天、30 天 | 1 小时 |
| 单节点详情 | 90 天 | 1 天 |

一分钟详情点对应一分钟桶内的上报；若该分钟缺少样本，页面保留空档，不用前后数据伪造。首页的五分钟桶只用于降低全节点响应体积和浏览器绘制成本，不会降低探针执行频率或删除一分钟原始样本。

### 首页当前值与 24 小时能量棒

节点卡片同时保留两个不同时间尺度，二者不能混为一谈：

- 首页格栅上方的数字来自**最新一轮探测**。ICMP 默认每轮 5 个 Echo，因此最新丢包率只会以 20% 递增；它用于判断线路此刻是否刚发生异常。TCP 探针只有延迟一条格栅。
- 下方 18 个能量棒色块压缩最近 24 小时，每个色块覆盖约 80 分钟。Worker 先输出 5 分钟桶，浏览器再将相邻桶合并为固定色块；它用于观察持续性和历史分布。
- 单节点详情中的 6/24 小时曲线继续使用一分钟点位，用于定位具体发生时间。

一次 5 个 Echo 全部失败，只能说明该分钟内的短探测窗口没有收到响应，不能据此宣称整分钟都处于中断状态。最新值有意保持敏感；80 分钟色块则采用更稳定的长期分级。

历史色块必须按实际样本数加权。对于色块内所有五分钟桶：

```text
色块丢包率 = (Σ attempted_samples - Σ successful_samples)
             / Σ attempted_samples × 100%
```

不得直接平均各桶的百分比，因为各桶的实际尝试数可能不同。历史丢包颜色固定为：

| 加权丢包率 | 颜色 | 含义 |
| ---: | --- | --- |
| `≤ 2%` | 绿色 | 正常或偶发波动 |
| `> 2%` 且 `≤ 10%` | 黄色 | 已确认的质量下降 |
| `> 10%` | 红色 | 严重质量下降 |
| 无样本 | 灰色 | 未知，不伪装成正常 |

为避免 80 分钟平均值掩盖短时严重故障，只要色块内任一 5 分钟桶的加权丢包率达到 60%，该色块直接标红。ICMP 探针配置中的 `warning_failure_percent` / `critical_failure_percent` 用于最新一轮的状态分级，不参与 24 小时历史色块分级；TCP 探针没有这两个配置。

延迟色块使用探针的 `warning_ms` / `critical_ms`；未配置时以近期中位数的 1.35 倍和 1.7 倍作为阈值。

## 7. 采集频率、去重与流量预算

- 模板默认每 60 秒采集并上报一次主机资源；
- 模板默认每 60 秒运行一轮已配置的 ICMP/TCP 探针；
- 每份报告携带最近一轮探针结果；Worker 以 `round_at + node_id` 整轮去重，不会把重试重复计入历史；
- 速率历史和整轮通信探针结果分别写入以时间开头的 `WITHOUT ROWID` 表，不为每个探针单独更新多份索引；
- Telegram 的 `/status` 和 `/panel` 只读取已持续采集的数据，不会临时触发额外探测。

两个间隔都可以在节点配置中调整。多节点免费部署应先根据探针总数和 D1 实际写入量核算；配置与下发步骤见[部署与管理](../guide.md#6-部署更新)。

典型 JSON 报告约 1–3 KB，每天 1,440 份约为 1.4–4.3 MB 正文；加上 HTTPS 上报及已配置的 ICMP Echo/TCP Connect 后，常见配置通常仍远低于 1 GB/月。实际值随探针数量和网络封装变化，应以服务商计数器为准。

中转 VPS 的业务流量与探针流量必须分开理解：同一份穿透业务通常在网卡上形成一次入站和一次出站。若服务商按双向合计计费，账面用量可接近用户有效穿透流量的两倍；这不是 Agent 重复发送数据。Agent 只读取网卡累计计数器，不抓包、不复制业务流量。

本项目不运行主动告警状态机，也不发送告警或日报。

## 8. 与主流开源探针的关系

这套实现使用的 Linux 主机计数器、ICMP Echo 和时间序列聚合，都是成熟且广泛使用的基础技术，但不存在一个要求所有监控软件采用完全相同统计口径的“官方唯一标准”。

源码对照：

- [Komari Agent 的探测任务](https://github.com/komari-monitor/komari-agent/blob/main/server/task.go)对一次任务发出一个 ICMP Echo，失败时以负值上报；[Komari 服务端](https://github.com/komari-monitor/komari/blob/main/web/rpc/jsonrpc/public.metric.go)按失败计数与总计数加权求丢包率。项目借鉴其“保留分子、分母再聚合”的原则，但不降低本项目每轮 5 个样本的精度；
- [Komari Next](https://github.com/tonyliuzj/komari-next/blob/main/src/components/Node.tsx)将丢包历史压缩成状态条。它的颜色阈值和分桶方式属于主题展示策略，并非协议标准，本项目根据 80 分钟窗口重新设定为 2%/10%；
- [哪吒 Agent 主程序](https://github.com/nezhahq/agent/blob/main/cmd/agent/main.go)同样采用多次 Echo，但只要收到至少一个响应就将该轮标记成功，仅返回平均 RTT。本项目不照搬这种折叠方式，而是保留每轮实际尝试数和成功数，因此能识别部分丢包；
- [SmokePing 官方说明](https://oss.oetiker.ch/smokeping/doc/reading.en.html)同样在一轮中发送多个包，以中位数表达延迟，并单独记录丢包；这与本项目采集层的设计最接近；
- [pro-bing](https://github.com/prometheus-community/pro-bing)是本项目采用的直接依赖；[iputils](https://github.com/iputils/iputils)是 Linux `ping` 等网络诊断工具的上游实现。

本项目刻意没有照搬主流项目常见的 raw-socket 特权模式、双向长连接、远程命令或 Agent 入站端口。保留的部分是成熟的 ICMP/TCP 测量原语、Linux 内核计数器和多样本统计；舍弃的是当前监控目标不需要的控制面复杂度。

## 9. 采集与展示一一对应

Agent 只采集节点配置中明确列出的检查，并且只上报页面或 Telegram 会用到的值；Worker 校验上报时逐字段读取，报告中多出的字段直接丢弃，不进入数据库。面板展示：

- 节点卡片展示全部探针（ICMP 三网参考、TCP 外部目标与节点互联，互联链路排在最后）。ICMP 为“名称 + 延迟格栅 + 丢包率格栅”，TCP 为“名称 + 延迟格栅”，最近 24 小时聚合成固定数量的状态时间格；
- CPU、内存和磁盘只在首页卡片显示紧凑占比圆环和容量；
- 节点详情分为“延迟”和“丢包率”两张曲线图，线路选择同时作用于两张图；丢包率图只包含 ICMP 探针，节点没有 ICMP 探针时不显示；缺失样本保留为曲线断点；
- 首页 24 小时能量格使用 5 分钟时间桶；单节点 6/24 小时详情使用 1 分钟时间桶，7/30 天和 90 天分别使用小时桶和每日汇总。

**展示过滤不是采集开关**：不再需要的探针必须从节点配置中删除；Agent 不会在配置之外生成或执行隐藏探针。面板通过探针 `kind`、`category` 和显示顺序动态选择内容，不依赖固定节点名、运营商名称或节点数量。

Worker 保存的 `source_ip` 是 Cloudflare 在该次 Agent HTTPS 上报连接上看到的源地址，只用于生成“上报源地址变化”事件（事件中地址已打码），不直接出现在网页或 Telegram `/status` 中；`source_country` 显示在节点详情的地区后。

## 10. 扩展规则

当前 Agent 和 Worker 只接受 `icmp` 与 `tcp`。未来若确有 TLS、HTTP 或其他协议需求，应作为新的完整功能重新评审，并同时处理：

1. Agent 配置校验、测量实现和模型；
2. Worker 报告校验与协议版本；
3. D1 结构升级和历史聚合；
4. 状态分级与准确术语；
5. 面板、Telegram 文案和测试；
6. 本文档中的测量语义与限制。

新增指标必须同时有展示位置；不得只采集不展示，也不得仅在界面增加一个名称而复用语义不相符的底层指标。

## 11. 隐私与开源边界

仓库只保存通用源码、数据库脚本、模板和保留域名/IP 示例。以下内容必须留在 Git 忽略的本机配置、Cloudflare Secrets 或服务器 `/etc/vpsmon/config.json` 中：

- 真实节点密钥、Bot Token、管理 Token 和绑定码；
- Cloudflare account/database ID、私有 Worker 地址；
- SSH 配置、真实公网 IP、主机名和节点清单；
- 生产报告、D1 导出、Telegram chat/user ID。

发布顺序为：数据库初始化或结构核对 → Worker 部署与版本核验 → 单个 Agent 更新与上报核验 → 扩大部署。任何生产数据都不应为编写测试或文档而复制进仓库。

## 12. 网卡与周期流量

- `network_interfaces` 为空时，分别选择 IPv4／IPv6 最低 metric 的有效默认路由。两者去重后只有一个接口才自动采用；没有默认路由或存在多个候选接口时，报告采集异常，不能退回所有接口相加。
- 显式列表最多 16 个实际接口，不能重复或包含 `lo`；可主动选择隧道接口。流量为所选接口计数器之和，避免同时选择承载同一流量的上下层接口。
- 速率由相邻有效报告的计数差除以采集时间差得到。启动标识、网卡集合或接口身份变化，以及计数回退、采集失败时，重新建立基线；未知值不显示为零速率。
- 流量只按 `traffic_cycle` 周期统计，首页显示为“周期流量”。重置日为 1–31，时区为 UTC 或 Asia/Shanghai；短月将重置日限制到月末。数据写入 `/var/lib/vpsmon/traffic.json`，使用私有权限和临时文件替换。
- 统计从 Agent 开始运行时起算，到下一个重置日 00:00 清零。只累计同一接口、同一次系统启动内的非负增量；系统重启、计数器重置或网卡重建只重新建立基线，不扣减已统计的流量。修改统计网卡、重置日或时区后从零开始；状态文件无法读取时同样从零开始。系统时间回拨时保留原状态。
- 跨越重置点的那次采样增量不计入任何周期，停采期间的流量也无法统计，因此周期值是估算，不保证与服务商账单一致。

## 13. 配置生效确认与页面刷新

Agent 校验配置文件后计算实际文件字节的 SHA-256 摘要，通过签名报告中的 `agent.config_fingerprint` 回传。管理工具核对配置摘要、Agent 版本和部署后的采集时间；迟到的暂存报告不能完成确认。摘要只用于核验，配置仍经 SSH 部署。

页面不可见时停止定时请求，恢复可见时刷新最新状态；历史缓存超过 5 分钟才重新读取。进行中的相同请求合并处理，认证失效后停止轮询。前端暂停不改变 Agent 采集频率或 D1 历史记录。

## 14. 上报失败与历史缺口

Agent 的 `pending.json` 只暂存**最新一份**失败上报。每轮先重试暂存报告，再采集和发送当前报告；当前报告仍失败时覆盖暂存，成功后清空。它不保证逐条补齐断网期间的历史资源、探针或事件样本。

周期流量先在本地 `traffic.json` 累计，再发送 HTTP。仅上报失败、但 Agent 仍正常采集时，周期累计继续；进程停采、系统重启和计数器变化按前述规则处理。
