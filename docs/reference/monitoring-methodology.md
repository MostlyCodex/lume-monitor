# 监测方法与技术实现

本文定义项目对“延迟、丢包、可达性”的准确含义，也是实现、历史存储和面板必须共同遵守的技术契约。

## 1. 设计目标

- 一个 Agent 二进制和一种配置结构适用于任意 Linux VPS。
- 基础主机监控始终存在；服务检查和通信探针按配置叠加。
- Agent 只发起出站连接，不监听端口、不执行远程命令、不修改业务服务。
- 通信探针只有 TCP Connect 一种，且只运行明确启用的；不携带 TLS、HTTP、登录或任意命令能力。
- **只采集、上报和保存页面或 Telegram 会展示的数据**；没有展示的指标不采集、不计算，也不存储。
- 使用当前数据库结构与上报格式；Worker 上线后逐台更新 Agent，并确认配置与新上报。

## 2. 通信探针语义

| 类型 | 实际操作 | 延迟含义 | 失败的表现 |
| --- | --- | --- | --- |
| `tcp` | TCP 三次握手后立即关闭 | 建立 TCP 连接的耗时 | **握手丢失率** |

探针分三类：三网参考（电信 / 联通 / 移动各一个目标，共用一个端口）、到其他节点（目标节点上本机能连上的端口）、到公网网址（每节点最多两个）。目标必须有本机能连上的开放端口。ICMP 已停用：国内运营商常过滤境外来的 Echo，TCP 也更接近真实业务流量。

TCP 握手丢失率按“超过 `connect_timeout_ms` 仍未完成的握手”计算。`connect_timeout_ms` 应低于 Linux 首个 SYN 的 1 秒重传时间（向导默认 900 ms）：超时设得更长时，一次 SYN 丢失会变成“重传后才连上”的高延迟成功，而不是一次丢失。握手失败可能来自链路、ACL、防火墙、监听服务或连接队列，不能单独定位根因。TCP 探针不发送 TLS ClientHello、HTTP 请求或应用数据，因此也不证明上层协议可用。

## 3. 单轮采样

每个探针按以下顺序运行：

1. 校验配置中的探针类型和目标格式；不接受命令行片段或任意 shell 输入。
2. 目标必须是单独的主机名或 IP，端口另用受限整数 `port` 字段；不接受 URL 或 shell 片段。
3. 按 `samples` 发起 1–10 次测量，相邻启动时间由 `sample_interval_ms` 控制。
4. `timeout_seconds` 是整轮上限。若时间耗尽，未启动的样本不会伪装成失败样本，该轮记为未完成。
5. Agent 上报请求数、实际尝试数、成功数和代表延迟。

Agent 未配置时默认每轮 3 个样本、间隔 250 ms；配置向导生成的探针每轮 5 个样本、单次超时 900 ms。单次 `connect_timeout_ms` 必须纳入整轮上限：

```text
(samples - 1) × sample_interval_ms + connect_timeout_ms
≤ timeout_seconds × 1000
```

不同目标的探针最多并行运行两项；同一探针的一轮样本按配置间隔启动。

## 4. 指标定义

设请求样本数为 `N`，实际尝试数为 `A`，成功数为 `S`，成功 RTT 集合为 `R`：

```text
丢包率 = (A - S) / A × 100%       （A > 0；A = 0 记为 100%）
```

- `duration_ms`：`R` 的中位数，作为一轮的代表延迟；
- 一轮只有在 `A = N` 且 `S > N/2` 时才标记为成功；`complete=false` 表示采样未完成，不能与目标丢包混为一谈；
- 一轮失败（多数握手未完成）时，首页延迟值显示为红色“— ms”；某个色块内完全没有成功样本时，该延迟色块为红色。

丢包率由 Worker 根据 `A` 与 `S` 计算，Agent 不再单独上报百分比。

## 5. 权限模型

TCP 探针使用 Go 标准库 `net.Dialer` 发起普通出站连接，不需要额外 capability，也不监听入站端口；Agent 没有第三方依赖。systemd unit 保持：

- `User=vpsmon`；
- `NoNewPrivileges=true`；
- 空的 `CapabilityBoundingSet` 和 `AmbientCapabilities`；
- 不以 root 运行。


## 6. 历史存储与颜色分级

D1 只保存页面会读取的历史：

| 数据 | 保留 | 用途 |
| --- | ---: | --- |
| 每分钟上传／下载速率、每轮探针结果 | 30 天 | 首页格栅、6 小时到 30 天的详情图 |
| 每日平均速率、每日探针汇总 | 90 天 | 90 天详情图 |
| 节点事件 | 90 天 | 详情页事件列表 |

每轮探针结果只保存名称、时间、是否成功、代表延迟、尝试数和成功数；每日汇总保存轮次、成功轮次、平均延迟和成功样本率。

页面按下表读取：

| 页面视图 | 时间范围 | 输出时间桶 |
| --- | ---: | ---: |
| 首页全节点能量格 | 24 小时 | 5 分钟 |
| 单节点详情 | 6 小时、24 小时 | 1 分钟 |
| 单节点详情 | 7 天、30 天 | 1 小时 |
| 单节点详情 | 90 天 | 1 天 |

一分钟详情点对应一分钟桶内的上报；若该分钟缺少样本，页面保留空档，不用前后数据伪造。首页的五分钟桶只用于降低全节点响应体积和浏览器绘制成本，不会降低探针执行频率或删除一分钟原始样本。

### 首页当前值与 24 小时能量棒

每个探针在节点卡片上占一行：延迟格栅左上角是探针名称、右上角是延迟值，丢包格栅右上角是丢包率；卡片顶部的“延迟 / 丢包”是两列的列标题。

- 延迟值来自**最新一轮探测**；丢包率是**最近 24 小时的加权丢包率**，与下方格栅口径相同。每轮只有 3–5 个样本，单轮丢包率只能以 20%–33% 跳变，不适合直接着色。
- 下方每条格栅 24 个色块压缩最近 24 小时，每个色块覆盖 1 小时；延迟、丢包两列等分卡片宽度，色块随列宽拉伸。Worker 先输出 5 分钟桶，浏览器再将同一小时的 12 个桶合并为一个色块；它用于观察持续性和历史分布。
- 单节点详情中的 6/24 小时曲线继续使用一分钟点位，用于定位具体发生时间；曲线颜色只区分线路，不表示状态。

三网参考只按运营商命名（电信、联通、移动），不记录目标所在城市；节点间链路只显示目标节点的名称，目标节点改名后自动跟随。

历史色块必须按实际样本数加权。对于色块内所有五分钟桶：

```text
色块丢包率 = (Σ attempted_samples - Σ successful_samples)
             / Σ attempted_samples × 100%
```

不得直接平均各桶的百分比，因为各桶的实际尝试数可能不同。延迟色块取色块内成功样本的平均延迟。

每个指标只有一把固定的尺子，色块与上方数值共用，所有探针相同：

| 颜色 | 延迟 | 加权丢包率 |
| --- | ---: | ---: |
| 绿色 | `< 80 ms` | `< 1%` |
| 蓝色 | `80–160 ms` | `1%–5%` |
| 黄色 | `160–240 ms` | `5%–20%` |
| 红色 | `≥ 240 ms`，或色块内无成功样本 | `≥ 20%` |
| 灰色 | 无样本 | 无样本 |

上方数值为绿色时保持正文颜色，只有偏离正常才着色。节点配置中的 `warning_ms`、`critical_ms`、`warning_failure_percent`、`critical_failure_percent` 不再参与面板着色。

节点卡片和详情页右上角只区分两种状态：正常上报时显示绿色圆点、“在线”和运行时长；超过 `stale_seconds` 未上报或尚无有效数据时显示置灰的“下线”。

## 7. 采集频率、去重与流量预算

- 模板默认每 60 秒采集并上报一次主机资源；
- 模板默认每 60 秒运行一轮已配置的 TCP 探针；
- 每份报告携带最近一轮探针结果；Worker 以 `round_at + node_id` 整轮去重，不会把重试重复计入历史；
- 速率历史和整轮通信探针结果分别写入以时间开头的 `WITHOUT ROWID` 表，不为每个探针单独更新多份索引；
- Telegram 的 `/status` 和 `/panel` 只读取已持续采集的数据，不会临时触发额外探测。

两个间隔都可以在节点配置中调整。多节点免费部署应先根据探针总数和 D1 实际写入量核算；配置与下发步骤见[部署与管理](../guide.md#6-部署更新)。

典型 JSON 报告约 1–3 KB，每天 1,440 份约为 1.4–4.3 MB 正文；加上 HTTPS 上报及已配置的 TCP Connect 后，常见配置通常仍远低于 1 GB/月。实际值随探针数量和网络封装变化，应以服务商计数器为准。

中转 VPS 的业务流量与探针流量必须分开理解：同一份穿透业务通常在网卡上形成一次入站和一次出站。若服务商按双向合计计费，账面用量可接近用户有效穿透流量的两倍；这不是 Agent 重复发送数据。Agent 只读取网卡累计计数器，不抓包、不复制业务流量。

本项目不运行主动告警状态机，也不发送告警或日报。

## 8. 与主流开源探针的关系

这套实现使用的 Linux 主机计数器、TCP 建连测量和时间序列聚合，都是成熟且广泛使用的基础技术，但不存在一个要求所有监控软件采用完全相同统计口径的“官方唯一标准”。

源码对照：

- [Komari Agent 的探测任务](https://github.com/komari-monitor/komari-agent/blob/main/server/task.go)支持 ICMP、TCP 和 HTTP，一次任务只测一次，失败时以负值上报；[Komari 服务端](https://github.com/komari-monitor/komari/blob/main/web/rpc/jsonrpc/public.metric.go)按失败计数与总计数加权求丢包率。项目借鉴其“保留分子、分母再聚合”的原则，但不降低本项目每轮 5 个样本的精度；
- [Komari Next](https://github.com/tonyliuzj/komari-next/blob/main/src/components/Node.tsx)将丢包历史压缩成状态条。它的颜色阈值和分桶方式属于主题展示策略，并非协议标准；本项目的四档颜色借鉴 [CF-Server-Monitor](https://github.com/huilang-me/CF-Server-Monitor) 前端“一个指标一把尺子”的做法；
- [哪吒 Agent 主程序](https://github.com/nezhahq/agent/blob/main/cmd/agent/main.go)的 ICMP 任务发多次 Echo，但只要收到至少一个响应就将该轮标记成功，仅返回平均 RTT。本项目不照搬这种折叠方式，而是保留每轮实际尝试数和成功数，因此能识别部分丢包；
- [monitor-probe](https://github.com/monitor-probe/agent) 与 [CF-Server-Monitor](https://github.com/huilang-me/cfsm-agent) 默认只用 TCP 握手测三网，并把超时卡在 1 秒左右，使丢失的 SYN 记为丢包而不是一次高延迟；本项目的 900 ms 超时出于同一理由；
- [SmokePing 官方说明](https://oss.oetiker.ch/smokeping/doc/reading.en.html)同样在一轮中发送多个包，以中位数表达延迟，并单独记录丢包；这与本项目采集层的设计最接近；

本项目刻意没有照搬主流项目常见的 raw-socket 特权模式、双向长连接、远程命令或 Agent 入站端口。保留的部分是成熟的 TCP 建连测量、Linux 内核计数器和多样本统计；舍弃的是当前监控目标不需要的控制面复杂度。

## 9. 采集与展示一一对应

Agent 只采集节点配置中明确列出的检查，并且只上报页面或 Telegram 会用到的值；Worker 校验上报时逐字段读取，报告中多出的字段直接丢弃，不进入数据库。面板展示：

- 节点卡片展示全部探针（三网参考、公网网址与节点互联，互联链路排在最后）。每个探针都是“延迟格栅 + 丢包率格栅”，名称在延迟格栅左上角，最近 24 小时聚合成每小时一格的状态时间格；
- CPU、内存和磁盘只在首页卡片显示紧凑占比圆环和容量；
- 节点详情分为“延迟”和“丢包率”两张曲线图，线路选择同时作用于两张图；缺失样本保留为曲线断点；点数超过图宽（每点至少 4 px）时按时间槽取平均后绘制，悬停数值与曲线一致，短时尖峰因此按所在时间槽摊薄；曲线用单调三次插值，不越过相邻样本的取值范围；
- 首页 24 小时能量格使用 5 分钟时间桶；单节点 6/24 小时详情使用 1 分钟时间桶，7/30 天和 90 天分别使用小时桶和每日汇总。

**展示过滤不是采集开关**：不再需要的探针必须从节点配置中删除；Agent 不会在配置之外生成或执行隐藏探针。面板通过探针 `kind`、`category` 和显示顺序动态选择内容，不依赖固定节点名、运营商名称或节点数量。

Worker 保存的 `source_ip` 是 Cloudflare 在该次 Agent HTTPS 上报连接上看到的源地址，只用于生成“上报源地址变化”事件（事件中地址已打码），不直接出现在网页或 Telegram `/status` 中；`source_country` 显示在节点详情的地区后。

## 10. 扩展规则

当前 Agent 和 Worker 只接受 `tcp`；数据库 `probe_catalog.kind` 的约束仍允许 `icmp`，仅为避免迁移，不会再写入。未来若确有 TLS、HTTP 或其他协议需求，应作为新的完整功能重新评审，并同时处理：

1. Agent 配置校验、测量实现和模型；
2. Worker 报告校验与协议版本；
3. D1 结构升级和历史聚合；
4. 状态分级与准确术语；
5. 面板、Telegram 文案和测试；
6. 本文档中的测量语义与限制。

新增指标必须同时有展示位置；不得只采集不展示，也不得仅在界面增加一个名称而复用语义不相符的底层指标。

## 11. 隐私与开源边界

仓库只保存通用源码、数据库脚本、模板和保留域名/IP 示例。以下内容必须留在 Git 忽略的本机配置、Cloudflare Secrets 或服务器 `/etc/vpsmon/config.json` 中：

- 真实节点密钥、Bot Token、管理 Token 和绑定码；
- Cloudflare account/database ID、私有 Worker 地址；
- SSH 配置、真实公网 IP、主机名和节点清单；
- 生产报告、D1 导出、Telegram chat/user ID。

发布顺序为：数据库初始化或结构核对 → Worker 部署与版本核验 → 单个 Agent 更新与上报核验 → 扩大部署。任何生产数据都不应为编写测试或文档而复制进仓库。

## 12. 网卡与周期流量

- `network_interfaces` 为空时，分别选择 IPv4／IPv6 最低 metric 的有效默认路由。两者去重后只有一个接口才自动采用；没有默认路由或存在多个候选接口时，报告采集异常，不能退回所有接口相加。
- 显式列表最多 16 个实际接口，不能重复或包含 `lo`；可主动选择隧道接口。流量为所选接口计数器之和，避免同时选择承载同一流量的上下层接口。
- 速率由相邻有效报告的计数差除以采集时间差得到。启动标识、网卡集合或接口身份变化，以及计数回退、采集失败时，重新建立基线；未知值不显示为零速率。
- 流量只按 `traffic_cycle` 周期统计，首页显示为“周期流量”。重置日为 1–31，时区为 UTC 或 Asia/Shanghai；短月将重置日限制到月末。数据写入 `/var/lib/vpsmon/traffic.json`，使用私有权限和临时文件替换。
- 统计从 Agent 开始运行时起算，到下一个重置日 00:00 清零。只累计同一接口、同一次系统启动内的非负增量；系统重启、计数器重置或网卡重建只重新建立基线，不扣减已统计的流量。修改统计网卡、重置日或时区后从零开始；状态文件无法读取时同样从零开始。系统时间回拨时保留原状态。
- 跨越重置点的那次采样增量不计入任何周期，停采期间的流量也无法统计，因此周期值是估算，不保证与服务商账单一致。

## 13. 配置生效确认与页面刷新

Agent 校验配置文件后计算实际文件字节的 SHA-256 摘要，通过签名报告中的 `agent.config_fingerprint` 回传。管理工具核对配置摘要、Agent 版本和部署后的采集时间；迟到的暂存报告不能完成确认。摘要只用于核验，配置仍经 SSH 部署。

页面不可见时停止定时请求，恢复可见时刷新最新状态；历史缓存超过 5 分钟才重新读取。历史只刷新当前显示的视图：停在节点详情时不轮询首页全节点历史，回到首页时缓存过期才补读。进行中的相同请求合并处理，认证失效后停止轮询。前端暂停不改变 Agent 采集频率或 D1 历史记录。

## 14. 上报失败与历史缺口

Agent 的 `pending.json` 只暂存**最新一份**失败上报。每轮先重试暂存报告，再采集和发送当前报告；当前报告仍失败时覆盖暂存，成功后清空。它不保证逐条补齐断网期间的历史资源、探针或事件样本。

周期流量先在本地 `traffic.json` 累计，再发送 HTTP。仅上报失败、但 Agent 仍正常采集时，周期累计继续；进程停采、系统重启和计数器变化按前述规则处理。
