# 监测方法与技术实现

本文定义项目对“延迟、丢包、采样覆盖率”的准确含义，也是实现、历史存储和面板必须共同遵守的技术契约。

## 1. 设计目标

- 一个 Agent 二进制和一种配置结构适用于任意 Linux VPS。
- 基础主机监控始终存在；服务检查和通信探针按配置叠加。
- Agent 只发起出站连接，不监听端口、不执行远程命令、不修改业务服务。
- 通信探针只实现明确启用的 ICMP Echo 或 TCP Connect；不携带 TLS、HTTP、登录或任意命令能力。
- nftables 观测是独立的本机数字计数模块，不复用通信探针语义，也不上传规则内容。
- 新字段向后兼容：先升级 D1/Worker，再逐台升级 Agent；旧 Agent 报告仍可被规范化。

## 2. 通信探针语义

| 类型 | 实际操作 | 延迟含义 | 失败比例的名称 | 适用场景 |
| --- | --- | --- | --- | --- |
| `icmp` | ICMP Echo 请求/响应 | 网络层 RTT | **丢包率** | 节点间基础链路质量、目标允许 ICMP 时 |
| `tcp` | TCP 三次握手后立即关闭 | 建立 TCP 连接的耗时 | **建连失败率** | ICMP 被过滤、需要观察指定端口可达性时 |

ICMP 丢包只能说明 Echo 报文未返回；它可能来自真实链路丢包，也可能来自目标或中间设备的 ICMP 限速或过滤，不能单独证明某个应用服务不可用。

TCP 建连失败可能来自链路、ACL、防火墙、监听服务或连接队列，不能单独定位根因。TCP 探针不发送 TLS ClientHello、HTTP 请求或应用数据，因此也不证明上层协议可用。Worker、面板和 Telegram 不会把 TCP 失败率标成丢包率。

## 3. 单轮采样

每个探针按以下顺序运行：

1. 校验配置中的探针类型和目标格式；不接受命令行片段或任意 shell 输入。
2. 目标必须是单独的主机名或 IP；ICMP 不接受端口，TCP 另用受限整数 `port` 字段，任何类型都不接受 URL 或 shell 片段。
3. 按 `samples` 发起 1–10 次测量，相邻启动时间由 `sample_interval_ms` 控制。
4. `timeout_seconds` 是整轮上限。若时间耗尽，未启动的样本不会伪装成失败样本，而由覆盖率单独反映。
5. Agent 将请求数、实际尝试数、成功数和统计值一起上报。

ICMP 默认 5 个样本，TCP 默认 3 个样本，间隔均为 250 ms。ICMP 配置必须满足：

```text
(samples - 1) × sample_interval_ms < timeout_seconds × 1000
```

TCP 还必须将单次 `connect_timeout_ms` 纳入整轮上限：

```text
(samples - 1) × sample_interval_ms + connect_timeout_ms
≤ timeout_seconds × 1000
```

不同目标的探针最多并行运行两项；同一探针的一轮样本按配置间隔启动。

## 4. 指标定义

设请求样本数为 `N`，实际尝试数为 `A`，成功数为 `S`，成功 RTT 集合为 `R`：

```text
采样覆盖率         = A / N × 100%
样本失败率         = (A - S) / A × 100%       （A > 0）
ICMP 丢包率        = 样本失败率                （kind=icmp）
TCP 建连失败率     = 样本失败率                （kind=tcp）
```

延迟统计只使用成功样本：

- `duration_ms`：`R` 的 p50（线性插值中位数），作为一轮的代表延迟；
- `average_duration_ms`：算术平均值；
- `p95_duration_ms`：p95（线性插值）；
- `min_duration_ms` / `max_duration_ms` / `range_ms`：最小、最大和极差；
- `jitter_ms`：本轮成功 RTT 的总体标准差 `sqrt(sum((x-mean)^2)/count)`。

“抖动”一词容易被不同实现定义为最大最小差或 RFC 3550 的平滑估计。本项目明确采用 **RTT 总体标准差**，面板也按此名称展示。

一轮只有在 `A = N` 且 `S > N/2` 时才标记为成功。`complete=false` 表示采样未完成，不能与目标丢包混为一谈。

## 5. 权限模型

Agent 直接使用 [`prometheus-community/pro-bing`](https://github.com/prometheus-community/pro-bing)，并固定为非特权模式 `SetPrivileged(false)`。Linux 上它使用 datagram ping socket，因此 systemd unit 继续保持：

- `User=vpsmon`；
- `NoNewPrivileges=true`；
- 空的 `CapabilityBoundingSet` 和 `AmbientCapabilities`；
- 不授予 `CAP_NET_RAW`，不以 root 运行。

主机内核的 `net.ipv4.ping_group_range` 必须允许 `vpsmon` 用户组使用非特权 ping socket。若发行版禁用了它，Agent 会报告 ICMP 不可用；项目不会静默切换到特权 raw socket。

TCP 使用 Go `net.Dialer` 发起普通出站连接，不需要额外 capability，也不监听入站端口。

nftables 规则计数需要 `CAP_NET_ADMIN`。该能力不授予常驻 Agent，而只保留给 timer 触发的短时 `vpsmon` oneshot。oneshot 读取配置指定的 chain，将规则内容在进程内归约为名称、累计计数和时间戳后写入 `0640` 数字快照；常驻 Agent 继续以无 capability 模式读取快照。配置为空时 timer 被关闭且快照删除。

## 6. 历史聚合与状态分级

D1 保存三层数据：

| 数据 | 默认保留 | 用途 |
| --- | ---: | --- |
| 原始主机/探针样本 | 30 天 | 精确诊断和短期趋势 |
| 小时聚合 | 400 天 | 中长期趋势 |
| 日聚合 | 730 天 | 长期基线 |

存储层的保留周期与页面的显示分辨率是两个概念。默认页面按下表读取同一批持续采集的数据：

| 页面视图 | 时间范围 | 输出时间桶 |
| --- | ---: | ---: |
| 首页全节点能量格 | 24 小时 | 5 分钟 |
| 单节点详情 | 6 小时、24 小时 | 1 分钟 |
| 单节点详情 | 7 天、30 天 | 1 小时 |
| 单节点详情 | 90 天 | 1 天 |

一分钟详情点对应一分钟桶内的上报；若该分钟缺少样本，页面保留空档，不用前后数据伪造。首页的五分钟桶只用于降低全节点响应体积和浏览器绘制成本，不会降低探针执行频率或删除一分钟原始样本。

聚合结果保留轮次成功率、成功样本率、采样失败率、采样覆盖率、延迟均值/最小/最大/p50/p95 和 RTT 标准差。只有 ICMP 将采样失败率公开为丢包率；TCP 的 `packet_loss_percent` 始终为空。

### 首页当前值与 24 小时能量棒

节点卡片同时保留两个不同时间尺度，二者不能混为一谈：

- 首页指标标题右侧的数字来自**最新一轮 ICMP**。默认每轮 5 个 Echo，因此最新丢包率只会以 20% 递增；它用于判断线路此刻是否刚发生异常。TCP 只在详情和按需状态中使用“建连失败”术语。
- 下方 18 个能量棒色块压缩最近 24 小时，每个色块覆盖约 80 分钟。Worker 先输出 5 分钟桶，浏览器再将相邻桶合并为固定色块；它用于观察持续性和历史分布。
- 单节点详情中的 6/24 小时曲线继续使用一分钟点位，用于定位具体发生时间。

一次 5 个 Echo 全部失败，只能说明该分钟内的短探测窗口没有收到响应，不能据此宣称整分钟都处于中断状态。最新值有意保持敏感；80 分钟色块则采用更稳定的长期分级。

历史色块必须按实际样本数加权。对于色块内所有五分钟桶：

```text
色块丢包率 = (Σ attempted_samples - Σ successful_samples)
             / Σ attempted_samples × 100%
```

不得直接平均各桶的百分比，因为各桶的实际尝试数可能不同。历史丢包颜色固定为：

| 加权丢包率 | 颜色 | 含义 |
| ---: | --- | --- |
| `≤ 2%` | 绿色 | 正常或偶发抖动 |
| `> 2%` 且 `≤ 10%` | 黄色 | 已确认的质量下降 |
| `> 10%` | 红色 | 严重质量下降 |
| 无样本 | 灰色 | 未知，不伪装成正常 |

为避免 80 分钟平均值掩盖短时严重故障，只要色块内任一 5 分钟桶的加权丢包率达到 60%，该色块直接标红。单轮探针配置中的 `warning_failure_percent` / `critical_failure_percent` 仍用于最新状态和链路分析，不参与 24 小时历史色块分级。

链路异常基线使用中位数和 MAD（median absolute deviation）：

```text
异常上限 = max(median × 1.5, median + 5ms, median + 4 × MAD)
```

固定阈值用于面板颜色和可解释的 SLA 判断；MAD 负责标记相对自身基线的突增。少量样本只作为观察信号，不应被解释为长期网络结论。

## 7. 采集频率、去重与流量预算

- 模板默认每 60 秒采集并上报一次主机资源；
- 模板默认每 60 秒运行一轮已配置的 ICMP/TCP 探针；
- 每份报告携带最近一轮探针结果；Worker 以 `round_at + node_id` 整轮去重，不会把重试重复计入历史；
- 资源历史和整轮通信探针结果分别写入以时间开头的 `WITHOUT ROWID` 表，不为每个探针单独更新多份索引；nftables 增量压入同一资源行，不增加 D1 历史行数；
- Telegram 的 `/status` 和 `/panel` 只读取已持续采集的数据，不会临时触发额外探测。

两个间隔都可以在节点配置中调整。多节点免费部署应先根据探针总数和 D1 实际写入量核算；容量与建议值见 [getting-started.md](getting-started.md#8-采集与探测频率)。

典型 JSON 报告约 1–5 KB，每天 1,440 份约为 1.4–7.2 MB 正文；加上 HTTPS 上报及已配置的 ICMP Echo/TCP Connect 后，常见配置通常仍远低于 1 GB/月。nftables 数字读取不产生网络流量。实际值随探针数量和网络封装变化，应以服务商计数器为准。

中转 VPS 的业务流量与探针流量必须分开理解：同一份穿透业务通常在网卡上形成一次入站和一次出站。若服务商按双向合计计费，账面用量可接近用户有效穿透流量的两倍；这不是 Agent 重复发送数据。Agent 只读取网卡累计计数器，不抓包、不复制业务流量。

本项目不运行主动告警状态机，也不发送告警或日报。探针配置中的延迟阈值和单轮失败率阈值彼此独立，用于最新一轮状态分级和链路分析；首页 24 小时丢包色块采用上一节定义的独立历史阈值。

## 8. 与主流开源探针的关系

这套实现使用的 Linux 主机计数器、ICMP Echo 和时间序列聚合，都是成熟且广泛使用的基础技术，但不存在一个要求所有监控软件采用完全相同统计口径的“官方唯一标准”。

源码对照：

- [Komari Agent 的探测任务](https://github.com/komari-monitor/komari-agent/blob/main/server/task.go)对一次任务发出一个 ICMP Echo，失败时以负值上报；[Komari 服务端](https://github.com/komari-monitor/komari/blob/main/web/rpc/jsonrpc/public.metric.go)按失败计数与总计数加权求丢包率。项目借鉴其“保留分子、分母再聚合”的原则，但不降低本项目每轮 5 个样本的精度；
- [Komari Next](https://github.com/tonyliuzj/komari-next/blob/main/src/components/Node.tsx)将丢包历史压缩成状态条。它的颜色阈值和分桶方式属于主题展示策略，并非协议标准，本项目根据 80 分钟窗口重新设定为 2%/10%；
- [哪吒 Agent 主程序](https://github.com/nezhahq/agent/blob/main/cmd/agent/main.go)同样采用多次 Echo，但只要收到至少一个响应就将该轮标记成功，仅返回平均 RTT。本项目不照搬这种折叠方式，而是保留每轮实际尝试数和成功数，因此能识别部分丢包；
- [SmokePing 官方说明](https://oss.oetiker.ch/smokeping/doc/reading.en.html)同样在一轮中发送多个包，以中位数表达延迟，并单独记录丢包；这与本项目采集层的设计最接近；
- [pro-bing](https://github.com/prometheus-community/pro-bing)是本项目采用的直接依赖；[iputils](https://github.com/iputils/iputils)是 Linux `ping` 等网络诊断工具的上游实现。

本项目刻意没有照搬主流项目常见的 raw-socket 特权模式、双向长连接、远程命令或 Agent 入站端口。保留的部分是成熟的 ICMP/TCP 测量原语、Linux 内核计数器和多样本统计；舍弃的是当前监控目标不需要的控制面复杂度。

## 9. 采集层与展示层边界

Agent 只采集节点配置中明确列出的检查；D1 保存这些已配置检查的完整技术指标，供历史诊断和后续算法使用。默认面板采用更窄的业务投影：

- 节点卡片只展示 ICMP 探针，每个目标固定为“名称、当前中位延迟、丢包率”一行，并将最近 24 小时聚合成固定数量的状态时间格；TCP 参与节点健康判断但只在详情显示；
- 延迟色块继续使用探针延迟阈值和历史分布；丢包色块按实际 Echo 数加权并采用独立的 2%/10% 长窗口阈值，任一五分钟桶达到 60% 时执行严重故障保护；无采样显示为独立的灰色空格；
- CPU、内存和磁盘只在首页卡片显示紧凑占比圆环，详情页不重复展示；
- 点击卡片进入独立节点详情；延迟使用连续曲线，ICMP 丢包或 TCP 建连失败使用同色竖向事件标记，浮窗使用各自准确术语，缺失延迟样本保留为曲线断点；
- 配置 nftables 计数时，详情额外出现“转发活动”数字卡与 30 天内命中速率曲线；未配置时整个模块不存在；
- 首页 24 小时能量格使用 5 分钟时间桶；单节点 6/24 小时详情使用 1 分钟时间桶，7/30 天和 90 天分别使用小时、日聚合；
- 每个已配置探针的 p95、RTT 标准差和采样覆盖率仍保留在历史数据中，但不占用默认业务视图。

这种分层避免为了界面简洁而删除仍有用途的诊断数据，也避免把实现细节直接堆到日常查看页面。**展示过滤不是采集开关**：不再需要的探针必须从 `/etc/vpsmon/config.json` 删除；Agent 不会在配置之外生成或执行隐藏探针。面板通过探针 `kind`、`category` 和显示顺序动态选择内容，不依赖固定节点名、运营商名称或节点数量。

Worker 内部保存的 `source_ip` 是 Cloudflare 在该次 Agent HTTPS 上报连接上看到的源地址，并不是 Agent 枚举出的完整公网地址清单。一次连接只会使用 IPv4 或 IPv6 其中一种；系统不会据此推断或伪造另一个地址族。该字段只用于私有审计和地址变化判断，不出现在网页界面或 Telegram `/status` 中。若未来确实需要采集双栈公网地址，应由 Agent 通过受控的 IPv4/IPv6 双栈自检单独上报，并明确其额外网络请求与失败语义。

## 10. 扩展规则

当前 Agent 和 Worker 只接受 `icmp` 与 `tcp`。未来若确有 TLS、HTTP 或其他协议需求，应作为新的完整功能重新评审，并同时处理：

1. Agent 配置校验、测量实现和模型；
2. Worker 报告校验与协议版本；
3. D1 向前迁移和历史聚合；
4. 状态分级与准确术语；
5. 面板、Telegram 文案和测试；
6. 本文档中的测量语义与限制。

不得仅在界面增加一个名称而复用语义不相符的底层指标。

## 11. 隐私与开源边界

仓库只保存通用源码、迁移、模板和保留域名/IP 示例。以下内容必须留在 Git 忽略的本机配置、Cloudflare Secrets 或服务器 `/etc/vpsmon/config.json` 中：

- 真实节点密钥、Bot Token、管理 Token 和绑定码；
- Cloudflare account/database ID、私有 Worker 地址；
- SSH 配置、真实公网 IP、主机名和节点清单；
- 生产报告、D1 导出、Telegram chat/user ID。

发布顺序为：D1 migration → Worker → Agent 小批量升级 → 观察后扩大部署。任何生产数据都不应为编写测试或文档而复制进仓库。
