# 监测方法与技术实现

本文定义项目对“延迟、丢包、连接失败、采样覆盖率”的准确含义，也是实现、历史存储、面板和后续扩展必须共同遵守的技术契约。

## 1. 设计目标

- 一个 Agent 二进制和一种配置结构适用于任意 Linux VPS。
- 基础主机监控始终存在；服务检查和通信探针按配置叠加。
- Agent 只发起出站连接，不监听端口、不执行远程命令、不修改业务服务。
- 指标名称必须对应实际测量对象，不能把 TCP/TLS 连接失败称为“网络丢包”。
- 新字段向后兼容：先升级 D1/Worker，再逐台升级 Agent；旧 Agent 报告仍可被规范化。

## 2. 三种探针的语义

| 类型 | 实际操作 | 延迟含义 | 失败比例的名称 | 适用场景 |
| --- | --- | --- | --- | --- |
| `icmp` | ICMP Echo 请求/响应 | 网络层 RTT | **丢包率** | 节点间基础链路质量、目标允许 ICMP 时 |
| `tcp` | 建立 TCP 连接 | TCP connect 耗时 | **连接失败率** | 端口可达性、真实传输路径 |
| `tls` | TCP 连接并完成 TLS 握手 | TCP + TLS handshake 耗时 | **连接失败率** | HTTPS/TLS 服务入口健康 |

ICMP 丢包只能说明 Echo 报文未返回；它可能来自真实链路丢包，也可能来自目标或中间设备的 ICMP 限速/过滤。TCP/TLS 失败同时受目标端口、服务负载、防火墙和握手状态影响，因此不能推断为 IP 层丢包。

## 3. 单轮采样

每个探针按以下顺序运行：

1. 校验配置中的探针类型和目标格式；不接受命令行片段或任意 shell 输入。
2. TCP/TLS 目标每轮只解析一次 DNS，并直接连接解析出的地址；DNS 时间不计入连接耗时。
3. 按 `samples` 发起 1–10 次测量，相邻启动时间由 `sample_interval_ms` 控制。
4. `timeout_seconds` 是整轮上限。若时间耗尽，未启动的样本不会伪装成失败样本，而由覆盖率单独反映。
5. Agent 将请求数、实际尝试数、成功数和统计值一起上报。

默认值：ICMP 为 5 个样本，TCP/TLS 为 1 个样本，间隔 250 ms。配置必须满足：

```text
(samples - 1) × sample_interval_ms < timeout_seconds × 1000
```

同一轮内的 TCP/TLS 尝试可能短暂重叠，以保证慢连接不会额外拉长整轮时间。探针总并发还受 Agent 内部信号量限制。

## 4. 指标定义

设请求样本数为 `N`，实际尝试数为 `A`，成功数为 `S`，成功 RTT 集合为 `R`：

```text
采样覆盖率         = A / N × 100%
样本失败率         = (A - S) / A × 100%       （A > 0）
ICMP 丢包率        = 样本失败率                （仅 kind=icmp）
TCP/TLS 连接失败率 = 样本失败率                （kind=tcp/tls）
```

延迟统计只使用成功样本：

- `duration_ms`：`R` 的 p50（线性插值中位数），作为一轮的代表延迟；
- `average_duration_ms`：算术平均值；
- `p95_duration_ms`：p95（线性插值）；
- `min_duration_ms` / `max_duration_ms` / `range_ms`：最小、最大和极差；
- `jitter_ms`：本轮成功 RTT 的总体标准差 `sqrt(sum((x-mean)^2)/count)`。

“抖动”一词容易被不同实现定义为最大最小差或 RFC 3550 的平滑估计。本项目明确采用 **RTT 总体标准差**，面板也按此名称展示。

一轮只有在 `A = N` 且 `S > N/2` 时才标记为成功。`complete=false` 表示采样未完成，不能与目标丢包混为一谈。

## 5. ICMP 权限模型

Agent 直接使用 [`prometheus-community/pro-bing`](https://github.com/prometheus-community/pro-bing)，并固定为非特权模式 `SetPrivileged(false)`。Linux 上它使用 datagram ping socket，因此 systemd unit 继续保持：

- `User=vpsmon`；
- `NoNewPrivileges=true`；
- 空的 `CapabilityBoundingSet` 和 `AmbientCapabilities`；
- 不授予 `CAP_NET_RAW`，不以 root 运行。

主机内核的 `net.ipv4.ping_group_range` 必须允许 `vpsmon` 用户组使用非特权 ping socket。若发行版禁用了它，Agent 会报告 ICMP 不可用；项目不会静默切换到特权 raw socket，也不会用 TCP 结果冒充丢包率。

## 6. 历史聚合与状态分级

D1 保存三层数据：

| 数据 | 默认保留 | 用途 |
| --- | ---: | --- |
| 原始主机/探针样本 | 30 天 | 精确诊断和短期趋势 |
| 小时聚合 | 400 天 | 中长期趋势 |
| 日聚合 | 730 天 | 长期基线 |

存储层的保留周期与页面的显示分辨率是两个概念。默认页面按下表读取同一批持续采集的数据：

| 页面视图 | 时间范围 | 输出时间桶 |
| --- | ---: | ---: |
| 首页全节点能量格 | 24 小时 | 5 分钟 |
| 单节点详情 | 6 小时、24 小时 | 1 分钟 |
| 单节点详情 | 7 天、30 天 | 1 小时 |
| 单节点详情 | 90 天 | 1 天 |

一分钟详情点对应一分钟桶内的上报；若该分钟缺少样本，页面保留空档，不用前后数据伪造。首页的五分钟桶只用于降低全节点响应体积和浏览器绘制成本，不会降低探针执行频率或删除一分钟原始样本。

聚合结果保留轮次成功率、成功样本率、样本失败率、采样覆盖率、延迟均值/最小/最大/p50/p95 和 RTT 标准差。ICMP 页面将失败率标为丢包率；TCP/TLS 页面将其标为连接失败率。

链路异常基线使用中位数和 MAD（median absolute deviation）：

```text
异常上限 = max(median × 1.5, median + 5ms, median + 4 × MAD)
```

固定阈值用于面板颜色和可解释的 SLA 判断；MAD 负责标记相对自身基线的突增。少量样本只作为观察信号，不应被解释为长期网络结论。

## 7. 采集频率、去重与流量预算

- 模板默认每 60 秒采集并上报一次主机资源；
- 模板默认每 60 秒运行一轮 ICMP/TCP/TLS 探针；
- 每份报告携带最近一轮探针结果；Worker 以 `round_at + node_id` 整轮去重，不会把重试重复计入历史；
- 资源历史和整轮探针结果分别写入以时间开头的 `WITHOUT ROWID` 表，不为每个探针单独更新多份索引；
- Telegram 的 `/status` 和 `/panel` 只读取已持续采集的数据，不会临时触发额外探测。

两个间隔都可以在节点配置中调整。多节点免费部署应先根据探针总数和 D1 实际写入量核算；容量与建议值见 [getting-started.md](getting-started.md#8-采集与探测频率)。

典型 JSON 报告约 1–4 KB，每天 1,440 份约为 1.4–5.8 MB 正文；加上 HTTPS、ICMP 和少量 TCP/TLS 握手后，常见配置通常仍远低于 1 GB/月。实际值随探针数量、TLS 连接复用和网络封装变化，应以服务商计数器为准。

中转 VPS 的业务流量与探针流量必须分开理解：同一份穿透业务通常在网卡上形成一次入站和一次出站。若服务商按双向合计计费，账面用量可接近用户有效穿透流量的两倍；这不是 Agent 重复发送数据。Agent 只读取网卡累计计数器，不抓包、不复制业务流量。

本项目不运行主动告警状态机，也不发送告警或日报。延迟阈值和失败率阈值彼此独立，仅用于当前状态分级、面板配色和历史分析；零值表示禁用对应分级。

## 8. 与主流开源探针的关系

这套实现使用的 Linux 主机计数器、ICMP Echo、TCP connect、TLS handshake 和时间序列聚合，都是成熟且广泛使用的基础技术，但不存在一个要求所有监控软件采用完全相同统计口径的“官方唯一标准”。

源码对照：

- [Komari Agent 的探测任务](https://github.com/komari-monitor/komari-agent/blob/main/server/task.go)使用 `pro-bing`，单任务上报一次 ICMP 结果；
- [哪吒 Agent 主程序](https://github.com/nezhahq/agent/blob/main/cmd/agent/main.go)同样引入 `pro-bing`，采用多次 Echo；
- [pro-bing](https://github.com/prometheus-community/pro-bing)是本项目采用的直接依赖；
- [iputils](https://github.com/iputils/iputils)是 Linux `ping` 等网络诊断工具的上游实现，可用于理解内核接口和传统工具行为。

本项目刻意没有照搬主流项目常见的 raw-socket 特权模式、双向长连接、远程命令或 Agent 入站端口。保留的部分是成熟测量原语和多样本统计；舍弃的部分是当前监控目标不需要的控制面复杂度。

## 9. 采集层与展示层边界

Agent 和 D1 保留完整技术指标，供历史诊断和后续算法使用。默认面板采用更窄的业务投影：

- 节点卡片只展示 ICMP 探针，每个目标固定为“名称、当前中位延迟、丢包率”一行，并将最近 24 小时聚合成固定数量的状态时间格；
- 时间格颜色由该时间桶的聚合延迟、加权丢包率和异常样本占比共同决定；无采样显示为独立的灰色空格，不伪装成正常；
- CPU、内存和磁盘只在卡片底部显示紧凑占比圆环，历史走势不与首页节点卡处于同一信息层级；
- TCP/TLS 结果不伪装成丢包率，也不与 ICMP 重复出现在网络质量列表；
- 点击卡片进入独立节点详情；延迟使用连续曲线，丢包使用同色竖向事件标记，浮窗同时给出精确值，缺失延迟样本保留为曲线断点；
- 首页 24 小时能量格使用 5 分钟时间桶；单节点 6/24 小时详情使用 1 分钟时间桶，7/30 天和 90 天分别使用小时、日聚合；
- p95、RTT 标准差、采样覆盖率和 TCP/TLS 失败率仍保留在历史数据中，但不占用默认业务视图。

这种分层避免为了界面简洁而删除诊断数据，也避免把实现细节直接堆到日常查看页面。面板通过探针 `kind`、`category` 和显示顺序动态选择内容，不依赖固定节点名、运营商名称或节点数量。

Worker 内部保存的 `source_ip` 是 Cloudflare 在该次 Agent HTTPS 上报连接上看到的源地址，并不是 Agent 枚举出的完整公网地址清单。一次连接只会使用 IPv4 或 IPv6 其中一种；系统不会据此推断或伪造另一个地址族。该字段只用于私有审计和地址变化判断，不出现在网页界面或 Telegram `/status` 中。若未来确实需要采集双栈公网地址，应由 Agent 通过受控的 IPv4/IPv6 双栈自检单独上报，并明确其额外网络请求与失败语义。

## 10. 扩展规则

新增探针能力时必须同时处理：

1. Agent 配置校验、测量实现和模型；
2. Worker 报告校验与旧版本规范化；
3. D1 向前迁移和历史聚合；
4. 状态分级与准确术语；
5. 面板、Telegram 文案和测试；
6. 本文档中的测量语义与限制。

不得仅在界面增加一个名称而复用语义不相符的底层指标。

## 11. 隐私与开源边界

仓库只保存通用源码、迁移、模板和保留域名/IP 示例。以下内容必须留在 Git 忽略的本机配置、Cloudflare Secrets 或服务器 `/etc/vpsmon/config.json` 中：

- 真实节点密钥、Bot Token、管理 Token 和绑定码；
- Cloudflare account/database ID、私有 Worker 地址；
- SSH 配置、真实公网 IP、主机名和节点清单；
- 生产报告、D1 导出、Telegram chat/user ID。

发布顺序为：D1 migration → Worker → Agent 小批量升级 → 启用新探针 → 观察后扩大部署。任何生产数据都不应为编写测试或文档而复制进仓库。
